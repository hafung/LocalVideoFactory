# 词组字幕高亮调研与实施建议

调研日期：2026-10-14。依据当时仓库代码、项目安装的 jieba 实际输出、已有独立 CLI 样片，以及上游官方资料。本文记录调研时的状态与设计建议，实现进展见下面补充。

实施补充（2026-10-14）：独立 CLI 0.2.0 已加入 cppjieba、用户词典、词/短语 JSON 和 ASS 当前组高亮；主应用已加入三种高亮粒度、原文范围、稳定字幕状态和通过 `|` 手动分组的编辑入口，可复用保存的词时间更新预览。下文“当前代码证据”保留调研时的状态。CLI 读取已有 JSON 的重分组命令、已知文案输入、关键词强调和模型语义分组仍属于后续阶段。

## 结论

可以实现，而且适合作为 VoxWeave 和独立 SenseVoice-CLI 的共同能力。

- **主应用已经内置分词和按词高亮**：使用 `@node-rs/jieba` 2.0.3；已知文案与识别结果先按字符匹配时间，再聚合成 jieba 词；视频渲染和应用 ASS 导出按当前词变色、放大。
- **独立 CLI 0.1.1 尚未内置分词**：输出模型 token 时间、VAD 区间和整句字幕；ASS 每句一条，没有词或短语高亮。中文模型 token 通常是字，不能当成中文词。
- **短视频所需的自然词组需要额外分组层**：分词回答“哪些字是一个词”，字幕分组回答“这一次一起强调哪几个词”。只增加 jieba 依赖不能完成后一项。
- **推荐基础方案是 jieba + 文本保护规则 + 停顿/标点 + 可编辑短语组**。主应用复用现有 Rust/Node 绑定；原生 C++ CLI 接 cppjieba。第一版无需增加语音模型、Python、LLM 或联网服务。

## 分词与短语的实际区别

在当前项目安装的 `@node-rs/jieba` 上直接执行 `cut(text, true)`：

| 输入 | 实际切词结果（省略标点） | 对字幕的含义 |
| --- | --- | --- |
| 今天教你三个提高效率的小技巧 | 今天 / 教 / 你 / 三个 / 提高效率 / 的 / 小 / 技巧 | “教 / 你”“的 / 小 / 技巧”单独闪烁会碎 |
| 只要三个步骤，就能做出高级感 | 只要 / 三个 / 步骤 / 就 / 能 / 做出 / 高级 / 感 | 可以期望高亮“只要 / 三个步骤 / 就能做出 / 高级感” |
| 这款产品只要199元，支持7天无理由退货 | 这 / 款 / 产品 / 只要 / 199 / 元 / 支持 / 7 / 天无 / 理由 / 退货 | 数字单位需要先保护；词典和短语规则也需要修正领域用语 |
| 用SenseVoice做AI字幕高亮，效果真的不错 | 用 / SenseVoice / 做 / AI / 字幕 / 高亮 / 效果 / 真的 / 不错 | 中英混排可用，但组合怎样强调仍需分组 |

上述目标分组是期望示例，不是已实现算法的输出。词性也只能作为软信号：样例中“感”被标为动词，“高亮”被标为 `x`，不能把词性当成可靠的语法解析结果。

已有 CLI 的 `preset-clean.json` 中，“才”是 9480–9960 ms，“刚刚开始”对应后续四个字，结束于 11526 ms。可以直接将它们聚合成“才刚刚开始”9480–11526 ms，无需重跑识别。另一个样片中，“交易”对应 1620–2100 ms，“几乎停滞”可以聚合为 2100–2940 ms。这里只证明现有时间信息可用于聚合，不代表人工测得了边界精度。

## 选型

| 方案 | 适用性 | 建议 |
| --- | --- | --- |
| 现有 `@node-rs/jieba` | `jieba-rs` 的 Node 绑定；项目已有词典、分词、词性、关键词功能 | 主应用继续使用 |
| cppjieba | C++ 头文件集成，支持 UTF-8、Windows、自定义词典、词性；无需另带 Python/Node 运行环境 | 独立 CLI 首选 |
| Python jieba | 可以让已有 Python 调用方自行后处理 JSON | 可作为外部使用示例；发行包不建议因此增加 Python |
| HanLP 等模型方案 | 可做分词、实体和句法分析；本地模型方案增加模型与推理依赖 | 有复杂语义分组需求时再做专项评测 |

这里推荐 cppjieba 的依据是它适合当前 CLI 的 C++ 构建与离线分发，**不是已经测得它的短语质量高于所有候选方案**。分组需求主要落在字幕规则层，换一个分词器仍然需要这层逻辑。

CLI 只带基础分词/HMM所需资源及许可证；第一版若不提供关键词提取，就不需要为它附带 TF-IDF 的 IDF 文件。固定上游版本与资源哈希，并验证中文资源路径、当前编译器、包外搬移运行。

Node 的 jieba-rs 与 cppjieba 不是同一实现。可以统一用户词典格式、规则和样例，但不能承诺切词完全相同。先做共同样例回归；只有产品需要严格一致时，再考虑把分词统一为同一个原生核心。

## 推荐的数据和处理流程

```text
音频 → SenseVoice/VAD → 原始声学 tokens
                              ↓
识别文字或已知文案 → 保留原文的字符映射
                              ↓
                金额/日期/单位/品牌等保护 → jieba 词
                              ↓
                标点、停顿、词典、时长 → 高亮短语组
                              ↓
                 字幕 cue 与排版 → 预览 / ASS / 视频
```

必须独立表达三个层次：

1. **声学 token**：模型给出的时间证据，保留原始结果与终点推算来源。
2. **字幕 cue**：屏幕上同时显示的文字及显示时间，可以包含多个高亮组。
3. **高亮 unit**：当前一起变色的连续文字范围，可以是字、词、短语或手选范围。

例如一条 cue 显示“只要三个步骤”，它内部先高亮“只要”，再高亮“三个步骤”。换行和换句不应被强制绑定到每次高亮切换。

建议保留现有应用 `tokens` 的词级信息，增加独立的 `highlightUnits`；CLI 保留原始 `tokens`，增加词级结果及 cue 内的高亮组。字段示意：

```ts
type HighlightUnit = {
  text: string;
  startChar: number; // cue.text 内 Unicode 码点偏移，闭区间起点
  endChar: number;   // 开区间终点
  startMs: number;
  endMs: number;
  timingSource: 'acoustic-derived' | 'estimated';
  groupingSource: 'rule' | 'manual';
};
```

字符范围用于准确重建标点、空格、中英混排和重复词；底层应保存到源 token 的映射。统一使用 Unicode 码点偏移，C++ 从 UTF-8 字节偏移转换，TS 使用 `Array.from()` 对应；不要混用 UTF-8 字节、UTF-16 code unit 和码点。

规范化、大小写折叠和 ITN 比较应使用单独的匹配视图，并保留到显示原文的映射。例如“二百元”和“200元”不能靠长度或第一次字符串搜索强行配时。模型 token 含多个字符而需要切开时，内部时间属于估计，必须标记来源。

旧 EditPlan 没有 `highlightUnits` 时继续使用现有词级高亮；新设置使用带默认值的可选字段并校验。CLI 采用明确的版本化扩展，文档说明新增字段及消费方迁移方式。

## 第一版分组规则

**先保护文本范围，再分词和合组**，避免“7 / 天无”这类结果让后续数字单位规则无法工作。

按以下优先级处理：

1. 手动指定的边界最高优先级；品牌、人名、固定短语词典参与自动处理，但不能覆盖手动拆分。
2. 句号、问号、感叹号，以及明确的语音停顿形成组边界；逗号等可按模板配置。跨明显停顿的长词也允许为字幕表现拆分。
3. 金额、百分数、日期、时长、数字单位和英文词内部不随意拆开；如“199元”“7天”“15%”“SenseVoice”。
4. 常见修饰语、数量与名词、助词与相邻实词做轻量合并；如“三个步骤”“小技巧”“做到了”。词性只作为辅助。
5. 根据字数和持续时间给候选边界评分，避免只按每 N 个字硬切。可从约 2–8 个汉字、0.4–1.5 秒的软目标开始调参；明显停顿、长专名和字幕宽度优先于软目标。这些数值尚未经过样片调优。
6. 超短组优先与相邻组合理合并；不为了达到最小时长跨句或跨停顿。无法可靠分组时降级为词级，而不是丢字幕或假造准确时间。

短语开始和结束优先取所覆盖字符/词的声学边界。现有 `next-token` 终点会包含部分停顿，不能仅靠 `next.start - previous.end` 检出全部停顿；还应使用 VAD 边界及时间来源。没有更细证据时保留估计性质，不把分组描述成时间精度提升。

切换短语期间保持稳定布局。暂停时可保留整条字幕并取消高亮；到 cue 结束再隐藏。ASS 可通过不重叠的完整文字状态事件实现，包含无高亮的间隙事件。

字幕粒度和视觉效果分开设置：粒度可以为“无动态高亮 / 按词 / 按短语”；视觉效果选择颜色、底框、轻微缩放。关键词强调另行选择自动或手动的少量重点范围，可以与短语跟读组合；不要把 TF-IDF top-K 直接当成口播重音。

## 独立 CLI 的建议接口

以下仅为拟议接口：

```powershell
sensevoice-cli.exe -i narration.wav `
  --highlight phrase `
  --user-dict terms.txt `
  -o result.json `
  --ass-output captions.ass
```

- `--highlight none|word|phrase`：默认保留现有整句 ASS 行为，显式开启时生成高亮。
- `--user-dict`：可选词典，品牌名、行业词、固定表达；词典不是语音识别热词，不会自动修复 ASR 识别错误。
- 通过 JSON 输出词/组范围及时间，方便外部编辑器自行渲染；不要让外部调用方只能解析 ASS 控制字符串。
- 后续增加独立的重分组输入模式，读取已有 JSON，无需为了改字幕再加载 ASR；手动范围文件也可在这一模式中应用。
- 后续增加已知文案输入与对齐，适合原文已知的配音工作流。主应用已有相应流程，CLI 需要单独实现与验证。

SRT 用于整句或短句文字和时间，不承载可移植的动态词组高亮。短语变色导出为 ASS 或视频烧录；各外部编辑器对 ASS 效果的导入需实测。

ASS 第一版推荐沿用应用的思路：每个高亮状态写完整字幕文本，仅当前范围加颜色。`\k` 是分段瞬时变色，`\kf` 是横向扫色，两者通常保留已唱过部分的主色；单独使用它们并不能准确表达“只有当前组亮、说完恢复”的效果。需要累计高亮/扫色时再增加对应模式。时间以百分之一秒量化，统一处理相邻事件舍入，避免把每条独立延长 10 ms 导致重叠。

## 主应用实施位置

- `shared/edit-plan.ts`：增加粒度设置、高亮组 schema 和旧计划兼容。
- `electron/composition/segmenter.ts`：提供保留标点和范围的字幕分词接口；现有关键词接口仍可保留简化输出。词典按项目实例隔离，避免当前模块全局 `jieba` 的词典累积影响其他项目。
- 新增纯分组模块：从文字范围、词和时间证据计算短语组，配规则配置与固定样例。
- `electron/alignment/align-text.ts`、`electron/composition/captions.ts`：对齐和估时路径均接入分组，并调整当前过短的 cue 策略。
- `electron/renderers/template-compiler.ts`、`electron/composition/subtitle-export.ts`：共享高亮状态计算，确保预览和 ASS 使用同一组范围。现有动态渲染按 token 显示，在时间间隙可能隐藏整条字幕；需要增加无高亮显示状态。
- `src/App.tsx` 及请求/IPC schema：把字幕风格和粒度分开；增加词组预览与合并、拆分、重点选择。用户改分组时从保存的时间映射重算，无需再生成音频。
- `tools/sensevoice-cli/`：加入 cppjieba、词典资源、范围映射、组 JSON 和 ASS 高亮导出。

分镜检索已经受益于 jieba，新增短语显示层主要改善字幕的阅读和节奏。检索仍可使用原有词/关键词表示，不必跟字幕高亮组保持同一粒度。

## 建议实施顺序和验收

1. **先做独立 CLI 的可见成果**：加入 cppjieba、用户词典、词/短语 JSON、ASS 当前组变色。用共同中文样例明确自动分组的行为。
2. **接主应用**：共享数据契约、分组规则和固定样例，增加粒度选择与稳定字幕布局；保持旧计划可打开。
3. **补编辑能力**：合并/拆分、重点选择、保存与重分组；按需增加 CLI 已知文案对齐、离线重分组模式。
4. **根据真实口播样片决定是否升级 NLP**：规则方案的错误集中在哪些句式，再对 HanLP/句法或可选 LLM 分组做质量、包体和耗时比较。模型只能提供原文边界建议，时间仍来自音频对齐。

第一阶段验收需要同时检查：

- 中文口播、电商数字单位、品牌新词、中英混排、重复词、标点、emoji、多字符 token、ITN 表示差异。
- 组文字无丢失或重复，范围和时间合法；明显停顿不被高亮跨过；估时部分可追溯。
- 帧上能够看到整个短语一起变色，其他部分保持正常；布局与换行稳定；ASS 在 libass 渲染通过。
- 旧 JSON/计划及无高亮调用可用；CLI 从项目外中文目录运行，无 Node/Python。
- 人工检查词组是否自然，以及高亮是否跟声音同步。当前样片没有人工时间标注，不能声称已经验证时间误差。

本次已实际跑 jieba 的四条示例，并读取三份既有 CLI 样片。复跑现有分词、字符对齐、ASS 导出和模板编译测试，排除构建副本后共 4 个测试文件、11 项测试，全部通过。未运行新算法、未重新识别音频、未安装候选依赖或测量 cppjieba 性能。
